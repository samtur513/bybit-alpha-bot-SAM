## 1. Введение и цели исследования

Range Mean-Reversion Engine (разработанный в рамках систем v3.2 Dual-Regime и v3.6 Omega ZF-8) представляет собой **ключевую альтернативную альфа-гипотезу** всего флота:
- В то время как 8 трендовых модулей эксплуатируют направленный импульс при высоких значениях трендовости ($ADX \ge 18–20$),
- Range Engine предназначен для сбора премии за ликвидность (Market Making / Fade Extremes) в стационарном флэте ($ADX < 18$, компрессия волатильности Боллинджера) путём расстановки пассивных Maker лимитов на внешних границах ($BB_{lower}$ / $BB_{upper}$) с фиксацией прибыли на средней скользящей ($SMA_{20}$).

**Цель исследования:**
1. Провести аудит исходного кода и выявить фундаментальные причины отсутствия сделок в live paper trading.
2. Ответить на 6 обязательных вопросов технического задания с указанием точных строк кода.
3. Провести строгий каузальный (Causal Zero-Lookahead) исторический replay на 1-часовых данных 18 монет Bybit за два независимых 90-дневных периода.
4. Сопоставить результаты с Baseline (простой возврат к средней без IRAS-фильтрации) и Random-контролем (случайные входы в том же режиме).

## 2. Экспертные ответы на 6 ключевых вопросов по v3.2 IRAS

### Вопрос 1: Проверить невозможность Maker Fill при использовании `next_bars_mock` с одинаковыми OHLC
- **Локализация:** `v3_2/src/paper_trader_v32.py`, строки 547–555:
  ```python
  next_bars_mock = {
      s: {
          "open": float(open_prices[s]),
          "high": float(open_prices[s]),
          "low": float(open_prices[s]),
          "close": float(open_prices[s]),
      }
      for s, b in bars.items()
  }
  self.range_engine.step_bar(
      timestamp=ts,
      bars=bars,
      next_bars=next_bars_mock,
      next_open_prices=open_prices,
      ...
  )
  ```
- **Правило исполнения в движке:** `v3_2/src/range_engine.py`, строки 230–238:
  ```python
  pen_buf = order.atr * Decimal("0.05")  # Требование пенетрации на 1-2 тика
  if order.direction == 1:
      # Buy limit fill: цена опустилась ниже лимита, а открытие бара выше или на лимите
      if next_low <= (order.price - pen_buf) and next_open >= order.price:
          filled = True
  elif order.direction == -1:
      # Sell limit fill: цена поднялась выше лимита, а открытие бара ниже или на лимите
      if next_high >= (order.price + pen_buf) and next_open <= order.price:
          filled = True
  ```
- **Математическое доказательство невозможности исполнения:**
  Для Buy Maker: поскольку в `next_bars_mock` $next\_low \equiv next\_open \equiv open\_prices[s]$, условие требует:
  $$open\_prices[s] \le (order.price - pen\_buf) \quad \land \quad open\_prices[s] \ge order.price$$
  Так как $pen\_buf > 0$, интервал $(-\infty, order.price - pen\_buf] \cap [order.price, +\infty) = \emptyset$.
  **Пересечение множеств пусто.** Ни одно число не может удовлетворять обоим неравенствам одновременно.
  Для Sell Maker условие требует аналогичного абсурда: $open\_prices[s] \ge order.price + pen\_buf \land open\_prices[s] \le order.price$.
- **Вывод аудита:** В реальном runtime `paper_trader_v32.py` и `paper_trader_v36.py` **вероятность исполнения любого Maker ордера была строго равна 0.000%**. Все размещаемые ордера гарантированно удалялись по таймауту TTL (2 бара).

### Вопрос 2: Проверить, почему KER не передаётся в классификатор режимов и заменяется на `0.10`
- **Локализация:** `v3_2/src/paper_trader_v32.py`, строки 518–531:
  Вызов `self.regime_classifier.classify_bar` передаёт 12 параметров, но параметр `ker` отсутствует в списке аргументов.
- **В сигнатуре функции:** `v3_2/src/regime_classifier.py`, строка 263:
  ```python
  def classify_bar(..., ker: float = 0.10) -> RegimeData:
  ```
- **Причина в коде (Forensic Discovery):**
  В `regime_classifier.py` условие режима CHOP:
  $$is\_chop = (ADX < 18.0) \land (KER \le 0.15) \land (\text{compressed} \lor \text{bandwidth} \ge 2.5\%)$$
  А в `range_engine.py` (строки 511, 542) условием входа в сделку является:
  $$\text{Long:} \quad RSI(14) < 35.0 \qquad \text{Short:} \quad RSI(14) > 65.0$$
  **Математическое противоречие индикаторов:**
  Kaufman Efficiency Ratio измеряет направленность движения:
  $$KER = \frac{|\Delta Price_{20}|}{\sum |\Delta Price_1|}$$
  Если $KER \le 0.15$, это означает, что за последние 20 баров цена практически не сместилась относительно суммарной волатильности (истинный белый шум). При таком движении 14-периодный RSI математически зажат в узком коридоре около 50 (эмпирически распределён между 35.65 и 65.50).
  Следовательно, при честном расчёте $KER \le 0.15$ событие $RSI < 35$ или $RSI > 65$ **практически никогда не наступает** (1 сигнал за 90 дней на 18 монетах).
  Автор кода столкнулся с полным отсутствием сигналов при включённом KER и решил проблему "в лоб": убрал передачу `ker` в классификатор, оставив дефолт `0.10`, который всегда меньше порогового `0.15`.

### Вопрос 3: Проверить значения KER / crossings / funding по умолчанию в IRAS Score
- **Локализация:** `v3_2/src/range_engine.py`, строки 498–504:
  ```python
  ker_val = float(b.get("ker", 0.06)) if "ker" in b else 0.06
  crossings_val = int(b.get("crossings", 5)) if "crossings" in b else 5
  funding_val = float(b.get("funding_rate", 0.0001)) if "funding_rate" in b else 0.0001
  velocity_mult = 0.5 + (min(crossings_val, 10) / 10.0)
  carry_mult = 1.0 + (abs(funding_val) * 200.0)
  iras_score = float(bw) * ((1.0 - min(ker_val, 0.99)) ** 2) * velocity_mult * carry_mult
  ```
- **Вывод аудита:**
  Поскольку входящие бары `bars` не содержали ключей `"ker"`, `"crossings"` и `"funding_rate"`, в формуле всегда подставлялись константы:
  $$\text{velocity\_mult} = 0.5 + \frac{5}{10} = 1.0$$
  $$\text{carry\_mult} = 1.0 + (0.0001 \times 200) = 1.02$$
  $$\text{iras\_score} = bw \times (1.0 - 0.06)^2 \times 1.0 \times 1.02 = bw \times 0.9012864$$
  Сложный институциональный скоринг IRAS в реальности был тривиальной константной функцией от ширины полосы Боллинджера ($0.9013 \times bw$).

### Вопрос 5: Проверить восстановление позиции, funding, TP/Stop и конфликт Range/Trend
- **Конфликт символов:** Взаимное исключение символов реализовано корректно на этапе входа: `sym in active_trend` запрещает вход в Range, а `s not in range_engine.open_positions` запрещает вход в Trend.
- **Regime Handoff:** Если открыта Range позиция, а на рынке начинается аномальный пробой ($ADX \ge 18$, объем $> 2.0 \times SMA_{20}$), Range Engine закрывает позицию по рынку с уплатой Taker fee (`REGIME_HANDOFF`), освобождая инструмент для трендового модуля.
- **Критический бухгалтерский дефект двойного Funding:**
  В `range_engine.py` при начислении funding (строка 207):
  ```python
  self.realized_equity += fpnl
  pos.funding_pnl += fpnl
  ```
  А при закрытии позиции (строки 366–367, 403–404, 435–436):
  ```python
  net_pnl = gross_pnl - exit_fee + pos.funding_pnl
  self.realized_equity += net_pnl
  ```
  Эквити получает `pos.funding_pnl` **дважды**. При длительном удержании позиций с положительным carry баланс Range Engine искусственно завышался.

## 4. Квант-анализ и интерпретация результатов

1. **Проблема голодания сигналов (Signal Starvation):**
   В режиме `IRAS_STRICT_KER` за 180 дней (4 320 баров на 18 монетах = 77 760 свечей) было сформировано всего **2 сделки**. Это математически подтверждает, что фильтр $KER \le 0.15$ и осциллятор $RSI < 35$ являются взаимно исключающими. Стратегия с такими параметрами не жизнеспособна из-за околонулевой частоты генерации сигналов.
2. **Несостоятельность фильтрации IRAS Score:**
   Результаты `IRAS_AUTHOR_KER` и `BASELINE` полностью совпали как в Period 1 (3 сделки, -$0.072), так и в Period 2 (8 сделок, -$7.537). Это доказывает, что при константном KER формула IRAS Score не осуществляет селективной фильтрации, а сделки генерируются исключительно базовыми полосами Боллинджера и порогом ширины диапазона $BW \ge 2.5\%$.
3. **Экономика Maker Reversal в Chop:**
   - **Win Rate:** составил лишь 0% в Period 1 и 12.5% в Period 2 (в среднем ~9.1%).
   - **Причина низкого Win Rate:** Ловля ножей на границах полос Боллинджера ($BB_{lower}$ / $BB_{upper}$) даже при $ADX < 18$ подвержена риску ложного пробоя. В 75–80% случаев цена выбивает стоп ($1.0 \times ATR$) до того, как успевает вернуться к средней ($SMA_{20}$).
   - **Сравнение с Random Control:** Случайные входы в том же режиме флэта демонстрируют катастрофическую просадку (-$221.98 и -$154.35, потеря более половины депозита), что подтверждает: торговля во флэте без направленного фильтра крайне токсична из-за трения спреда и комиссий.
4. **Статистика исполнения ордеров (Fill Ratio):**
   - В среднем исполняется от **33% до 61%** выставленных Maker-лимитов.
   - Около 40–60% ордеров (`missing_fills`) истекают по таймауту, поскольку цена разворачивается, не доходя 1–2 тика до границы, либо гэпает мимо лимита.

## 5. Рекомендации по интеграции в Paper V2

1. **Не запускать Range Engine в исходном виде с $KER \le 0.15$:** это приводит либо к полному отсутствию сделок, либо (при дефолте $0.10$) к отрицательному математическому ожиданию ($PF = 0.24$).
2. **Пересмотр триггера входа:**
   Вместо крайних значений RSI ($<35$ / $>65$), которые требуют импульса, для флэта требуется использовать **осциллятор стохастик или Williams %R**, либо входить лимитом при касании границы канала Keltner с фильтром по объёму поглощения.
3. **Исправление тестового и live контура:**
   Заменить генерацию `next_bars_mock` в `paper_trader_v32.py` и `v36` на реальный поток очереди ордеров из `UniversalFleetExecutionAdapter`.
4. **Устранить двойной учёт Funding:**
   Привести бухгалтерские проводки Range к стандарту `FleetFinancialLedger`.
