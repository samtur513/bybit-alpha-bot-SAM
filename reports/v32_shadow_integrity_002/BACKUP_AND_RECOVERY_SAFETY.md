## 1. Официальный отзыв статуса безопасности скрипта `create_vps_atomic_snapshot.sh`

Настоящим документом **официально отзывается статус «безопасного для исполнения»** (SAFE_TO_EXECUTE) у скрипта `create_vps_atomic_snapshot.sh`, предложенного в отчёте V32-MASTER-001.

### 1.1. В чём заключалась опасность `PRAGMA wal_checkpoint(TRUNCATE)`
В исходном плане предлагалось выполнять на живом VPS следующую команду:
```bash
sqlite3 "$db" "PRAGMA wal_checkpoint(TRUNCATE);"
```
с последующим вызовом обычного файлового копирования `cp` / `rsync`.

Данный подход категорически нарушает стандарты целостности высоконагруженных квантовых баз данных:
1. **Блокировки и сбои торговых потоков (Deadlock / SQLITE_BUSY)**:  
   Режим `TRUNCATE` требует эксклюзивной блокировки базы данных (`EXCLUSIVE lock`), чтобы сбросить все страницы из файла `-wal` в основной `.db` и усечь файл WAL до нулевого размера. Если в этот момент торговый движок бота выполняет чтение или транзакционную запись нового рыночного события, внешняя команда `sqlite3` либо зависает, либо падает с кодом `SQLITE_BUSY (database is locked)`, либо блокирует запись ордеров и стопов движка на бирже, провоцируя проскальзывание и сбой асинхронного цикла.
2. **Рассинхронизация и «разрыв» страниц при обычном файловом копировании (Torn DB Pages)**:  
   Даже если чекпоинт завершился, живой процесс бота **продолжает писать** новые кадры WAL в следующую микросекунду. Обычное копирование (`cp live.db backup.db` и затем `cp live.db-wal backup.db-wal`) не является атомарным на уровне файловой системы ОС. В момент копирования `.db` файл может содержать одно состояние заголовка и salt-номеров, а в момент копирования `.db-wal` файл уже модифицирован новыми транзакциями. При попытке открыть такой архив на резервном стенде SQLite выдаёт ошибку `SQLITE_CORRUPT (database disk image is malformed)` либо необратимо повреждает B-Tree индексы.

## 2. Безопасная процедура резервного копирования: SQLite Online Backup API

Единственным стандартным и безопасным способом снятия согласованной копии активной базы данных SQLite в режиме WAL без остановки пишущих процессов и без блокировки торговых потоков является **SQLite Online Backup API** (`sqlite3_backup_init`, `sqlite3_backup_step`, `sqlite3_backup_finish`).

В интерфейсе командной строки SQLite это выполняется командой `.backup`:
```bash
sqlite3 /opt/bybit-bot/v3_10_sweep/tca_attribution.db ".backup /backup/atomic/tca_attribution_backup.db"
```
В среде Python:
```python
import sqlite3

def safe_online_backup(src_db_path: str, dst_db_path: str) -> None:
    src_conn = sqlite3.connect(src_db_path, timeout=30.0)
    dst_conn = sqlite3.connect(dst_db_path)
    try:
        with dst_conn:
            # Копирование порциями по 100 страниц с кооперативным снятием блокировок
            src_conn.backup(dst_conn, pages=100)
    finally:
        dst_conn.close()
        src_conn.close()
```

### Преимущества Online Backup API:
- **Согласованность на уровне страниц**: Все страницы из файла `.db` и активного журнала `.db-wal` объединяются в единый, полностью согласованный файл `.db`, не требующий наличия WAL для открытия.
- **Неблокирующее чтение**: Читающий поток бэкапа не накладывает эксклюзивных блокировок и уступает дорогу пишущим торговым транзакциям бота.
- **Автономность**: Полученный файл `destination.db` полностью самодостаточен, проверен и готов к немедленному переносу на изолированный стенд.

## 3. Протокол проверки резервных копий на изолированном стенде

Простая распаковка архива (`tar -tzf` или `tar -xzf`) признана **недостаточной** для подтверждения статуса `RESTORE_VERIFIED`.

Обязательный регламент приёмки резервной копии:
1. Восстановление архива во временную изолированную директорию (sandbox).
2. Подключение к восстановленной SQLite-БД и выполнение аппаратной проверки:
   ```sql
   PRAGMA integrity_check;
   ```
   Результат должен быть строго равен `ok`.
3. Сверка контрольных сумм схем и подсчёт количества записей:
   ```sql
   SELECT count(*) FROM shadow_execution_events;
   ```
4. Проверка целостности JSON-состояний (`json.loads`) и сверка ключей инвариантов.
Данный протокол автоматизирован и подтверждён тестом `tests/test_v32_backup_recovery_safety.py::test_sqlite_online_backup_api_integrity` (100% PASS).

## 4. Исключение секретов из публикуемых архивов (Secrets Sanitization)

В любые создаваемые скрипты и архивы резервного копирования вводится жёсткая маска секретных данных:
- Файлы `.env` категорически **запрещено** включать в открытые git-архивы или отчёты без предварительной фильтрации.
- Все ключи, содержащие подстроки `API_KEY`, `API_SECRET`, `BOT_TOKEN`, `PASSWORD`, автоматически заменяются на значение:
  `***MASKED_FOR_RESEARCH_SAFETY***`.
Реализация и проверка маскирования зафиксированы в тесте:  
`tests/test_v32_backup_recovery_safety.py::test_secrets_sanitization_in_backup_filter` (100% PASS).

## 7. Разрешение противоречий Donchian 1H/4H и Cascade TP1/TP2/TP3

В ряде предыдущих отчётов присутствовали противоречия относительно таймфрейма и уровней фиксации прибыли v3.2. Настоящий аудит устраняет эти противоречия на основе проверки исходного программного кода.

### 7.1. Таймфрейм Donchian: СТРОГО 1H (НЕ 4H)
- В `v3_2/src/config.py`:
  - Строка 63: `CANDLE_INTERVAL = "60"` (60 минут = 1 час).
  - Строка 64: `BAR_INTERVAL_MS = 1 * 3600 * 1000` (3 600 000 мс).
  - Строка 65: `DONCHIAN_WINDOW = 120` (120 баров = 5 торговых суток).
  - Строка 6-7: *«TREND Regime: 1h Donchian Breakout (120 bars)»*.
- **Вывод**: Оригинальная система v3.2 на порту 8083 построена на **1-часовом** Donchian Breakout. Конфигурация 4H относится к v3.0 и v3.1.4 (порт 8084), с которыми v3.2 была ошибочно отождествлена в черновых заметках.

### 7.2. Структура Cascade Take Profit: СТРОГО TP1 (30%) + TP2 (40%) + Runner (30%) (НЕТ TP3)
- В исполняемом модуле `v3/src/core_v3.py` (строки 84–88, 328–360):
  - `tp1_r_mult = Decimal("1.5")`, `tp1_ratio = Decimal("0.30")`: при достижении прибыли $+1.5 \times \text{ATR}$ закрывается 30% объёма позиции, стоп-лосс переносится в безубыток (`entry_price`).
  - `tp2_r_mult = Decimal("3.0")`, `tp2_ratio = Decimal("0.40")`: при достижении прибыли $+3.0 \times \text{ATR}$ закрывается ещё 40% исходного объёма, стоп-лосс переносится на уровень гарантированной прибыли ($+1.5 \times \text{ATR}$ от входа).
  - Оставшиеся 30% объёма позиции являются **бегущей позицией (Runner)**, которая удерживается до противоположного пробоя канала Donchian либо динамического трейлинг-стопа.
- **Вывод**: В оригинальном коде v3.2 **нет отдельного триггера TP3**. Формулировки вида «TP1/TP2/TP3» или уровни «1.8 / 3.2 / 5.0 ATR» являлись внешними эвристиками и отвергаются в пользу точного следования программному коду ядра.
